## 三、发现的共性问题

### 3.1 `extra=forbid` + `response_model` → 静默 500

**问题链**:
1. Pydantic schema 定义 `model_config = ConfigDict(extra='forbid')`（126 个 schema 使用了此配置）
2. FastAPI endpoint 使用该 schema 作为 `response_model=SomeDTO`
3. 路由处理函数通过 `_*_dict()` helper 返回一个 dict
4. **当 helper 返回的字段名/类型与 schema 不匹配时**，Pydantic 在响应序列化阶段抛出 `ResponseValidationError`
5. FastAPI 将 `ResponseValidationError` 转换为 HTTP 500，但 DB 事务可能已提交（数据已持久化）
6. 前端收到 500 或空数据，但**操作实际上成功了**——数据不一致

**已知触发过此问题的端点**:
| 文件 | Schema | helper 函数 | 问题 |
|------|--------|-------------|------|
| `product_baselines.py` | `ProductBaselineSummaryDTO` | `_bl_summary_dict` | `_ci_latest_revision` 返回 string，schema 要 dict |
| `accounts.py` | `UserDTOExtended` | `_account_to_dict` | 多了 `enabled` 字段 |
| `workflow_models.py` | `WorkflowModelDTO` | dict literal | 字段名 `"tasks"` vs schema 的 `"taskModels"` |

**防御方案**:
- 新写 helper 函数时，对照 schema 逐字段核对
- `extra=forbid` 对请求体安全有用，对响应体风险高——考虑将响应 schema 改为 `extra='ignore'`
- 或者编写自动化测试：遍历所有 `response_model` 端点 → 调用 API → 检查是否有 500

### 3.2 前端字段名按 Payara DTO 严格对齐

**铁律**: 前端 JSON 字段名 = Payara Java DTO 字段名，不能自己编。

**已知不匹配**:
| Payara DTO | Python 代码误用 | 影响 |
|------------|----------------|------|
| `PartTemplateCreationDTO.reference` | `body.get("id")` | 创建模板时读不到值 → 空 ID |
| `PartMasterTemplateDTO.attachedFile` (String, 单数) | `attachedFiles: list` (复数) | 模板附件不显示 |
| `ActivityModelDTO.taskModels` (List) | dict key `"tasks"` | workflow-models 返回 500 |
| `DocumentRevisionDTO.creationDate` (Date) | `creation_date.isoformat()` (String) | 类型不匹配 |

**防御方案**: 写任何新端点返回数据前，先查 Payara 的 DTO 类确认字段名、类型、单复数。

## 八、铁律提醒

1. **对齐 Payara 是铁律** — 前端字段名、DTO 字段名、API 响应格式必须和 Payara/Java 一致，不自己发明
2. **容器不能 rebuild** — 网络不通，必须用 `docker cp` + `docker restart`
3. **`extra=forbid` 是双刃剑** — 请求体用它安全，响应体用它危险。写 helper 函数时必须逐字段核对 schema
4. **Nginx 双端口同步更新** — Port 80 和 Port 85 的 location 规则必须同步改动
5. **测试前先 `pytest`** — 176 passed 1 skipped 是基线，任何改动不能退化
